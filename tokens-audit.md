# Аудит дизайн-токенів Nestwood (`ui/kit.css`)

Read-only дослідження. Жоден файл проєкту не змінено. Джерела: `ui/kit.css` (211 токенів у `:root`, перевизначення в `[data-theme="dark"]`), усі 33 сторінки `wireframes/*.html`, перелічені в завданні, плюс `ui/kit.html` як окремий споживач (вітрина компонентів кіта — сама не частина продукту).

**Метод.** `ui/kit.css` розібрано програмно: 211 токенів у `:root` (`--ic-s/-m/-l/-glass` — розміри іконок, а 30 окремих `--ic-<назва>` — самі SVG-маски, винесені в окрему таблицю в кінці розділу 1). Для кожного токена знайдено всі місця вживання `var(--токен)` у правилах `ui/kit.css` (з урахуванням вкладених `@media`), для кожного селектора — усі класи, а для кожного класу — грепом перевірено, у яких із 33 сторінок (+`kit.html`) цей клас реально присутній у розмітці. Це дає ланцюжок «токен → властивість CSS → клас → сторінка», а не здогад.

**Важливе обмеження методу**: «файли» в таблиці — це сторінки, де сам **клас** присутній у розмітці; для селекторів-тегів без класу (напр. `form + p`) греп по класу нічого не знаходить, хоча правило може реально спрацьовувати — такі рядки позначені окремо, а не як «не використовується».

**Скоуп 33 сторінок**, як у завданні: catalogue(-empty), new-plan(+conflict/error/loading), huts(-empty; фактичний файл — `hut.html`, окремого списку `huts.html`/`huts-empty.html` в репо теж є — обидва враховано), hut, notes(-empty), plans(-empty), plan(+past/error/offline), day(+seasonal/intrip/offline), booking, gear, share, guide, lodging-system, safety, first-aid, me, my-gear, membership, settings, account, flow — усього 33 файли в `wireframes/*.html`, плюс `ui/kit.html` окремо позначений у колонці «файли», але не входить у скоуп «продукту».

## 1. Таблиця токенів

211 токенів: 181 «звичайний» (колір, шрифт, відступ, радіус, розмір, тінь, рух) + 30 SVG-іконок-масок (окрема компактна таблиця в кінці розділу — для кожної іконки й так один змістовний рядок: маска, а не набір різних властивостей).

Формат ролі: `<властивість-CSS-по-українськи> (<клас(и) селектора>)`. Де в одному рядку кілька вживань — усі перелічені через «;». `— (не перевизначено)` означає: токен не має свого запису в `[data-theme="dark"]`, тобто в темній темі використовується те саме світле значення (навмисно чи ні — див. розділ 2).

## 2. Дрейф значень

### 2.1. `--link` і `--blue` розходяться саме там, де мали б збігатися

- Світла тема: `--blue: #2D5BFF`, `--link: #2D5BFF` — однакові.
- Темна тема: `--blue: #3A66F5`, `--link: #7C9BFF` — **різні**.

Обидва токени в світлій темі описують один і той самий відтінок «сигнального синього», і `--link` вживається саме там, де очікувано альтернативне ім'я для «дії, вираженої текстом» (`.shell__back`, `.shell__close`, `.brief__action`, `.action-text`, `.btn--text` — усі: `color: var(--link)`), а `--blue` — там, де дія виражена заливкою/обвідкою (`.btn--primary` фон, фокус-кільце полів, `.switch`/`.check` у стані «увімкнено», `.spinner`/`.row--loading` індикатор завантаження). У світлій темі це узгоджено (одне й те саме значення під двома іменами). У темній темі хтось свідомо обрав для посилань світліший, більш «блідий» відтінок (`#7C9BFF`) — ймовірно, заради контрасту тексту на темному тлі — але не поширив цю зміну на `--blue`. Це або (а) недокументований намір «посилання в темній темі мають бути світлішими за кнопки», який ніде текстом не зафіксований, або (б) забуте оновлення — `--blue` мали підняти так само, як підняли `--link`, і не зробили. У будь-якому разі це дрейф: та сама роль «акцентний синій, дія» в одній темі — один колір, в іншій — два різні.

### 2.2. Дублювання кольору hex-літералом замість `var()` у складених токенах — системний патерн

Чотири «тіньові/обвідкові» шорткоди в `:root` не посилаються на вже наявні кольорові токени через `var()`, а дослівно повторюють їхнє hex-значення, і це дублювання доводиться вручну синхронізувати в обох темах:

| Складений токен | Значення light | Дублює | Значення dark | Дублює |
|---|---|---|---|---|
| `--e-hair` | `inset 0 0 0 1px #D9DCDF` | `--hairline` (`#D9DCDF`) | `inset 0 0 0 1px #34383C` | `--hairline` dark (`#34383C`) |
| `--e-stroke` | `inset 0 0 0 1.5px #D9DCDF` | `--hairline` | `inset 0 0 0 1.5px #34383C` | `--hairline` dark |
| `--e-hair-bottom` | `inset 0 -1px 0 #D9DCDF` | `--hairline` | `inset 0 -1px 0 #34383C` | `--hairline` dark |
| `--e-focus-ring` | `0 0 0 4px #E8EEFF` | `--blue-soft` (`#E8EEFF`) | `0 0 0 4px #1D2A55` | `--blue-soft` dark |

Наразі всі чотири синхронізовані правильно (значення дійсно збігаються в обох темах), тож це не помилка сьогодні — але це крихка конструкція: якщо колись `--hairline` або `--blue-soft` зміняться, ці чотири композитні токени доведеться згадати й підняти вручну окремо, бо CSS-змінні тут не посилаються одна на одну. Формально це та сама роль («колір волосяної лінії», «колір м'якого синього фокус-кільця»), записана двічі різними механізмами — це і є дрейф-ризик, а не дрейф по факту.

### 2.3. Дві різні бази «майже чорного» для однієї ролі «затемнення/тінь»

Роль «напівпрозоре затемнення фото чи підкладки» представлена в токенах двома різними базовими кольорами:

- на основі **ink** (`#0F1113`): `--dim: rgba(15,17,19,.5)`, `--glass-btn: rgba(15,17,19,.45)`, `--glass-btn-strong: rgba(15,17,19,.6)`, `--dim-layer` (не використовується, теж на основі `15,17,19`);
- на основі **чистого чорного** (`#000000`, ніде не визначеного як токен кольору): `--scrim-top`, `--scrim-bottom`, `--shadow-text`, `--e-float`, `--e-sheet`, `--e-photo-floor`, `--shadow-title`, `--shadow-card` — усі використовують літерал `rgba(0,0,0,…)`.

Візуально відмінність мінімальна (`#0F1113` vs `#000000`), але це буквально два різні джерела істини для «яким чорним затемнювати»: скляні кнопки й діммер модалки — одним, а скрими фото й усі тіні глибини — іншим. Жодного текстового обґрунтування цього поділу в самому файлі немає (коментарі описують лише групи «колір» і «глибина», не пояснюють вибір бази). Кандидат на об'єднання або явну фіксацію причини.

### 2.4. `--sos-bg` — застиглий дублікат `--conflict`, не прив'язаний до теми

`--sos-bg: #B42318` дослівно дорівнює світлому `--conflict` (`#B42318`), але, на відміну від `--conflict` (який у темній темі стає `#FF7A6B`), **`--sos-bg` не перевизначений у `[data-theme="dark"]`** і залишається `#B42318` в обох темах. Те саме стосується `--sos-fg` (`#FFFFFF`, теж без dark-перевизначення). Це може бути свідомим рішенням («SOS завжди такий самий тривожний червоний, незалежно від теми» — цілком захисна логіка для безпекового елемента), але текстом це рішення ніде не зафіксовано, а сам факт, що один токен виведений з іншого лише значенням, а не посиланням, і поводиться інакше в темі — це дрейф на межі з навмисною відмінністю. Вартий явного запису як рішення, а не мовчазного розбіжного значення.

### 2.5. Чотири «майже білих поверхні» з різними альфа й відтінком

Роль «світла напівпрозора підкладка/скло» представлена чотирма токенами з чотирма різними точними значеннями:

- `--surface: #FFFFFF` (непрозорий, чиста картка)
- `--panel-bg: rgba(250,250,250,.9)` (не білий — трохи сірий, 250/250/250, і напівпрозорий)
- `--bar-bg: rgba(255,255,255,.88)` (білий, інша альфа)
- `--chip-photo: rgba(255,255,255,.92)` (білий, третя альфа)
- `--attrib-bg: rgba(255,255,255,.7)` (білий, четверта альфа)

Кожен зі своєю роллю (картка / панель complications на фото / нижня панель-бар / чіп на фото / плашка атрибуції) — тобто це, найімовірніше, **навмисна** диференціація «наскільки прозоре скло» залежно від контексту, а не помилка. Але `--panel-bg` вирізняється тим, що це єдиний з п'яти не суто білий, а зміщений у `250,250,250` — варто перевірити, чи це навмисний ледь сірий відтінок для панелі «Прилад», чи випадкове відхилення при копіюванні значення.

## 3. Одна змінна на кілька несумісних ролей

### 3.1. `--blue` — не лише «дія»

`concept.md`/`CLAUDE.md` фіксують: «Signal blue `#2D5BFF` = action colour (buttons, links)». У коді `--blue` (не `--link`) реально відповідає за:

1. **Дію/CTA** — `.btn--primary { background: var(--blue) }`.
2. **Стан «увімкнено» перемикача й чекбокса** — `.switch:checked`, `.check:checked { background: var(--blue) }`. Це не кнопка дії, а індикатор бінарного стану «так/увімкнено» — семантично ближче до ролі «підтвердження вибору», ніж до «натисни, щоб щось сталося».
3. **Фокус-кільце полів** — `.field__input:focus`, `.search-float__input:focus-visible { box-shadow: inset 0 0 0 var(--stroke-strong) var(--blue), var(--e-focus-ring) }` — роль «фокус клавіатури/доступності», третя за змістом.
4. **Індикатор завантаження** — `.spinner`, `.row--loading::before { border-top-color: var(--blue) }` — роль «процес виконується», ще один самостійний смисл.

Це чотири різні комунікативні задачі («зроби це» / «це увімкнено» / «сюди зараз фокус» / «зачекай, триває процес»), об'єднані одним кольором. Для акцентного кольору бренду це звична практика (один сигнальний колір скрізь, де це «синя нитка» інтерфейсу), але це не одна роль «дія», як сформульовано в дизайн-документах, — і якщо колись знадобиться відрізнити наприклад «фокус» від «дія» (напр. в темному in-trip режимі, де синій зчитується гірше), доведеться розплутувати одну змінну на чотири.

### 3.2. `--ink` — текст, фон «натиснутого» стану і фон інверсної плашки одночасно

- **Текст**: майже всі `color: var(--ink)` — заголовки, значення, підписи (переважна більшість використань).
- **Фон вибраного стану контролу**: `.chip[aria-pressed="true"] { background: var(--ink) }`, `.seg > a[aria-current="page"] { background: var(--ink) }` — тут ink стає заливкою «натиснутого» чіпа/сегмента, а колір тексту на ній переходить у `--glass` (див. рядок `--glass` у таблиці: `.chip`, `.seg > a[aria-current="page"] { color: var(--glass) }`) — тобто пара ink/glass інвертується як типова пара «фон/текст на активному контролі».
- **Фон інверсної алерт-панелі**: `--alert-bg: #0F1113` світлому дорівнює `--ink` дослівно (значення однакове), і використовується як фон інверсної плашки-алерту («inverted ink panel with hatched edge» з concept.html) — це третя роль, зафіксована окремим токеном (`--alert-bg`), що просто випадково дорівнює `--ink` у світлій темі, але в темній темі вже НЕ дорівнює (`--alert-bg: #26292D` ≠ `--ink` dark `#F2F3F4`) — тобто в темній темі роль «інверсна панель» коректно відокремлена від ролі «текст», а в світлій — випадково збігається значенням, хоч і різними іменами.

Разом: `--ink` як сирий токен виконує дві ролі (текст і фон вибраного стану) в самому CSS, а третя споріднена роль (фон алерту) вже винесена в окремий токен — непослідовність у тому, наскільки глибоко проведена ця сепарація.

### 3.3. `--graphite` — другорядний текст і заливка декоративних елементів

Основна роль — колір другорядного тексту (підписи, лічильники, підказки полів — більшість використань). Але той самий токен також вживається як **фон**, а не колір, у кількох місцях: `.row::after` (роздільник/лінія в рядку), `.list--icons .row::before` (маркер-крапка), `.day::after`, `.day--transport::before`, `.limit::before`, `.cond::before`, `.disclosure > summary::after` (стрілка розкриття). Тобто «сірий графітовий» одночасно є і кольором тексту, і кольором маленьких декоративних заливок (крапки, лінії, стрілки) — друга роль ближче до «нейтральний елемент інтерфейсу», ніж до «текст».

### 3.4. `--hairline` — межа і «порожня» заливка одночасно

Основна роль — колір тонкої лінії-межі (`border-*: var(--hairline)` на картках, списках, панелях). Але вживається і як **фон**: `.profile-id__avatar` (заглушка аватара), `.scale__step` (невибраний крок шкали складності), `.days > li::before`, `.sheet--first::before`, `.switch` (трек вимкненого перемикача), `.skeleton` (заглушка завантаження). Тут роль — «нейтральний, майже непомітний плейсхолдер», що семантично інше, ніж «межа/розділювач», хоч і той самий відтінок логічно підходить для обох (обидві ролі — «майже непомітно»).

## 4. Значення повз змінні

Результат грепу hex-кольорів, inline `style="…"` і `<style>`-блоків по всіх 33 сторінках `wireframes/*.html`:

- **Жодна з 33 сторінок не містить inline `style="…"` атрибутів і жодна не містить локального `<style>`-блоку.** Це підтверджено грепом (`style="` по всіх 33 файлах — 0 збігів; `<style` по всіх 33 файлах — 0 збігів). Тобто на рівні розмітки продукту хардкодів немає взагалі — усе оформлення йде виключно через класи з `ui/kit.css`. Це саме по собі сильний позитивний результат аудиту.
- **`wireframes/account.html`, рядок 167** — єдине місце в усіх 33 сторінках, де в розмітці зустрічається hex-колір: `#4285F4`, `#34A853`, `#FBBC05`, `#EA4335` у `fill="…"` атрибутах усередині inline-SVG логотипа Google (кнопка «Continue with Google»). Це не хардкод токена дизайн-системи — це офіційні бренд-кольори чужого логотипа (Google), які за визначенням не можуть бути токенізовані під наш кіт. Не вважаю це знахідкою дрейфу; фіксую лише для повноти грепу.
- **`ui/kit.html`** (не входить у 33 сторінки, але прямо згаданий у завданні як окремий споживач) має власний `<style>`-блок (рядки 8–34) із доброю дюжиною hex-кольорів (`#E9EAEA`, `#141414`, `#fff`, `#cfcfcf`, `#4a4a4a`, `#F4F5F5`, `#e3e3e3`, `#D6D6D6`) і px-значень. Файл сам це документує коментарем на рядку 9: `/* Рамка вітрини — не частина кіта */` — тобто це свідомо визнаний виняток: хром сторінки-вітрини (шапка з перемикачем теми, сітка карток, таблиця API) навмисно не побудований на токенах кіта, бо це інструмент перегляду кіта, а не сам кіт. Єдине трохи неоднозначне місце — рядок 264, де `#2149E0` (точне значення `--blue-pressed`) згадано **в тексті пояснення** (`<p class="note">…Натиснута головна — #2149E0…</p>»), а не в CSS-декларації — це документальна згадка значення для читача вітрини, не хардкод стилю.
- **`wireframes/ia.html`** (документ-рідбек мапи інформаційної архітектури, не входить у список 33 продуктових сторінок) містить 15 inline `style="width:…px"` (ширини колонок таблиць) і кілька hex (`#8b978f`, `#e0796b`, `#7fc0a2`, `#9cc4ec` з альфою `22`) для кольорових прямокутників легенди в самому документі. Це поза скоупом аудиту (не продуктова сторінка з `_generate.py`/`TREE`), тому не вважаю знахідкою проти кіта — просто фіксую, що вона існує, на випадок якщо ia.html колись переплутають із продуктовою сторінкою.

**Підсумок розділу 4**: жодного реального хардкоду токена (кольору, відступу, радіуса) у розмітці 33 аудійованих сторінок не знайдено — дисципліна «усе через класи кіту» витримана повністю. Єдині винятки — чужий бренд-колір (Google-логотип) і явно позначена рамка вітрини `kit.html`, яка сама себе виключає коментарем.

## 5. Кандидати в семантичні ролі

| Роль | Токен(и)-кандидат(и) зараз | Де фактично несе роль | Один явний переможець чи конкуренція |
|---|---|---|---|
| **Фон сторінки** | `--glass` | `.nw` (корінь продукту), `.shell` (кожен екран) | Один явний токен, конкурентів немає. |
| **Фон картки** | `--surface` | `.panel--card`, `.list`, `.days`, `.day`, `.profile`, `.sheet`, `.field__input`, `.chip`, `.seg`, `.check`, `.disclosure`, усі `.shell--sheet` шари | Один явний токен для «непрозорої картки». Але поруч існує сімейство напівпрозорих «скляних» поверхонь (`--panel-bg`, `--bar-bg`, `--chip-photo`, `--attrib-bg`, `--glass-btn`, `--glass-btn-strong`) — це **інша, сусідня роль** («скло на фото»), не заміна `--surface`, і в кожного своя альфа (див. 2.5) — тобто в межах «скла» переможця нема, там п'ять конкурентів на одну підроль. |
| **Текст основний** | `--ink` | Переважна більшість `color:` у кіті (заголовки, значення, підписи, лейбли) | Один явний токен — але той самий токен подвоює роль «фон вибраного стану» (див. 3.2), тож як «чистий» токен тексту він не ізольований. |
| **Текст другорядний** | `--graphite` (і його буквальний дублікат-алiас `--dash` для пунктирних меж, `--on-disabled`/`--attrib-fg`, що теж дорівнюють `--graphite` за значенням) | `.shell__footer`, `.tabbar__item`, `.row__sub`, `.panel__unit`/`__label`, `.note`, `.field__hint`, `.disclosure > p` тощо | Один явний «головний» токен (`--graphite`), але навколо нього — щонайменше три токени з тим самим hex (`--dash`, `--on-disabled` light, `--attrib-fg`), кожен під своєю назвою для своєї підролі. Це не дрейф (значення всюди узгоджені), але це означає, що «другорядний сірий» насправді іменований чотирма різними способами. |
| **Дія (accent/CTA)** | `--blue` та `--link` | `--blue`: `.btn--primary`, фокус-кільця, `.switch`/`.check` увімкнено, спінер; `--link`: `.shell__back`/`.shell__close`, `.brief__action`, `.action-text`, `.btn--text` | Два конкуруючі токени, що в світлій темі — один колір під двома іменами, а в темній темі реально розходяться (розділ 2.1). Це рівно той випадок «кілька токенів з майже однаковим hex», який шукає розділ 2. |
| **Довіра/підтвердження (успіх/fixed)** | `--fixed` + `--fixed-soft` | `.pill--fixed` (колір і фон), `.field--ok` (обвідка й текст підказки) | Пара токенів (насичений + м'який фон) з чіткими, неконкуруючими ролями — це, на відміну від «дії», приклад чистого, без дрейфу, розв'язання ролі. |
| **Небезпека/конфлікт (error)** | `--conflict`, `--conflict-on-ink`, `--on-conflict`, і окремо `--sos-bg`/`--sos-fg` | `--conflict`: `.btn--danger`, `.btn--danger-fill`, `.field--error`; `--conflict-on-ink`: `.alert--conflict` (дублює dark-варіант `--conflict`, розділ 2 не рахує це дрейфом — це навмисний «конфлікт на темному тлі»); `--sos-bg`/`--sos-fg`: лише `.btn--sos` | Три-чотири токени на одну загальну роль «тривога», кожен свідомо прив'язаний до свого контексту (звичайна помилка / помилка на інверсній плашці / кнопка SOS) — але жоден з них не документований як «навмисно незалежний від теми», крім самого факту відсутності dark-перевизначення в `--sos-bg`/`--sos-fg`/`--conflict-on-ink`. Явного єдиного «переможця» нема — це сімейство, а не один токен, і межі навмисності варто зафіксувати текстом. |

**Додаткові ролі, виявлені за фактом вживання (не було у вихідному списку):**

- **Жива позначка на приладі / увага** — `--yellow` + `--yellow-ink`. Чітко одна роль, один явний переможець, жодної конкуренції (`.tabbar__badge`, `.pill--attention::before`, `.scale__step--active`, `.day--warn::before`, `.alert__tag`) — саме так, як і задекларовано в CLAUDE.md («hi-vis yellow = only live state on the instrument»). Єдиний токен цієї ролі не перевизначається в темній темі — і це узгоджено з написаним правилом «hi-vis yellow ніколи не змінюється», тобто це задокументований, а не випадковий інваріант.
- **Скло на фото / підкладка над зображенням** — сімейство `--glass-btn`, `--glass-btn-strong`, `--on-photo`, `--on-photo-soft`, `--scrim-top`, `--scrim-bottom`, `--panel-bg`, `--bar-bg`, `--chip-photo`, `--attrib-bg`/`--attrib-fg`. Це найбільш «розгалужена» роль у всій системі — 10+ токенів, кожен із власною алгеброю прозорості, без жодного з них явно «головного». Вартий окремого проходу, якщо колись знадобиться уніфікувати кількість відтінків скла.
- **Розмежувач/плейсхолдер (нейтральний, не межа й не текст)** — `--hairline`, коли він вживається як `background`, а не `border-color` (розділ 3.4). Ця підроль ще не має власного імені, хоч і використовує чужий токен.

## Підсумок

- **211 токенів** у `:root` (`ui/kit.css`): 181 «звичайний» (колір/шрифт/відступ/радіус/розмір/тінь/рух) + 30 SVG-іконок-масок.
- **9 токенів не використовуються жодним класом** ніде в `ui/kit.css`, а отже й на жодній із 33 сторінок: `--map-water`, `--fs-18`, `--fs-32` (останні два — тільки в демонстраційному `ui/kit.html`, у продуктових класах не задіяні), `--ls-num`, `--ls-0`, `--s-14`, `--h-map`, `--h-panel`, `--dim-layer`.
- **Компонент без застосування**: `.btn--round` (`ui/kit.css:550`) визначений, але не зустрічається в жодній з 33 сторінок і навіть у `ui/kit.html`.
- **Розмітка продукту чиста**: 0 inline `style=`, 0 локальних `<style>` на всіх 33 сторінках; єдиний hex поза кітом — бренд-кольори логотипа Google в `account.html` (легітимний виняток, не токен дизайн-системи).
- **5 знахідок дрейфу** (розділ 2): розбіжність `--link`/`--blue` між темами; системне дублювання hex замість `var()` у чотирьох композитних тінях (`--e-hair`, `--e-stroke`, `--e-hair-bottom`, `--e-focus-ring`); дві різні бази «чорного» для затемнень і тіней (ink-based vs чистий `#000`); `--sos-bg`/`--sos-fg` як застиглий, не прив'язаний до теми дублікат `--conflict`; чотири близькі, але не ідентичні «майже білих» скляних поверхні.
- **4 випадки «одна змінна — кілька ролей»** (розділ 3): `--blue` (дія / стан «увімкнено» / фокус / завантаження), `--ink` (текст / фон вибраного стану / випадковий збіг з фоном алерту), `--graphite` (другорядний текст / декоративні заливки-крапки-лінії), `--hairline` (межа / нейтральний плейсхолдер-заливка).
- **Додаткова знахідка в іконках**: 3 з 5 вкладок таб-бару (`guide`, `safety`, `profile`) не мають окремої «жирної» іконки для активного стану — `--ic-on` дорівнює звичайному `--ic` дослівно, на відміну від `map` і `plans`.
